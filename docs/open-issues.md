# 未解决的问题

这份文件只记**还没做完**的事。修完的条目从这里删掉，实测与取舍写进 [design.md](design.md)（按轮次编年）——所以这里的编号会变，不要在别处引用它。2026-09-24 已经修掉并从这里移走的：家目录 dotfiles 免审、出沙箱命令不说 argv0 落点、docker socket 只靠 bwrap 丢组、旧默认值钉在配置文件里没人说（都在 design.md 的「第二十二轮」）。README 也在同一天拆成了 README＋[reference.md](reference.md)，所以「README 太长」那条一并移走了。2026-10-04 检查 9/22 到 10/3 的十二天日志时另修了五处（分页器卡住、慢文件系统上 worktree 被当成植入、凭据清单缺 shell 历史、`manage_task send_input` 免审、读本会话任务输出要审），都在「第二十四轮」，没进过这份清单；同一轮稍后又修掉了清单里的「装上去的副本比仓库旧，没人知道」、「agy 被杀掉之后，后台标记永远不清」和「审核对话把用户自己的 agy 对话挤掉」。

判据两条，和 design.md 一致：

- **会不会多一次让人决策的弹窗**——会，就是退步，哪怕它更安全；
- **会不会比 Codex 更弱**——会，就不做；更严可以，前提是仍然由审核模型或确定性规则自动判。

多一次自动审核是可以接受的代价，多一次弹窗不是。

条目里的数字都是真机实测，来源是 `~/.gemini/autoagy/logs/decisions.jsonl`：早先的条目用的是 2026-09-22、2026-09-23 两天的正常使用（约 1500 次操作、121 次审核），2026-10-04 加的条目用的是 2026-09-22 到 10-03 的十二天（约 1.07 万次工具调用、834 次审核）。

## 一、正常使用会碰到的

### 1. 审核慢、且花你自己的额度（优先级：高，但插件只能改一半）

**证据**：guardian 用的是用户自己的 Antigravity 账号。第一天中位数 4.3 秒；第二天 9.1 秒，63 次里 23 次超过 40 秒、13 次落在 60～80 秒、7 次在期限处超时。慢的集中在主 agent 跑 docker＋仿真的那几个小时，晚上轻活时 18 次只有 2 次慢。已排除本机因素：同一台机器空载 2～5 秒，6 个核心全部跑满 4.5～5 秒，prompt 换成真实的 1.6 MB 对话记录 2.1 秒。

**已做**：超时改为重问（第二十一轮），README 把这件事说清楚。

**还能做**：① 常驻一个 guardian 进程，省掉每次起一个完整 agy（现在每次审核都要启动语言服务器）；② 支持给 guardian 配独立账号或更快的模型——`reviewer.agy.model` 和 OpenAI 兼容后端都已经有了，缺的是实测过的推荐值；③ 压缩送审 prompt（现在 50～87 KB，大头是对话摘要）。

### 2. 会写 `.git` 的 git 命令被审两次（优先级：中）

**证据**：`git checkout -- <files>` 这类命令先在沙箱里按 `dangerous-command` 审一次（实测 20 秒、69 秒），因为 `.git` 是只读挂载所以失败，agent 再加 `BypassSandbox` 重试，又审一次。两天各出现 3 次。最贵的一条是 2026-09-23 11:03–11:09 的 `git checkout`：第一次审 20 秒，随后两次 escalation 各在 90 秒超时被拒，一条命令花掉 3 分半。

**可能的做法**：沙箱内确定会写 `.git` 的 git 子命令直接拒绝，并在理由里说明"改用 `BypassSandbox: true` 重试"。这是**拒绝**而不是放行，所以不弱于 Codex；省掉的是一次注定失败的执行和一次注定要重做的审核。

**风险**：子命令判断必须保守。`git status`、`git log`、`git diff`、`git config --get`、裸 `git branch`／`git tag`（列表）都不写 `.git`，误判会把本来能在沙箱里免审跑完的命令推去审核——那是净退步。所以只放确定会写的形态（`add`／`commit`／`checkout`／`switch`／`restore`／`reset`／`worktree`／`stash` 非 list／`merge`／`rebase`／`cherry-pick`／`revert`）。

### 3. 必须出沙箱的工具，每条都要审（优先级：低，目前接受）

**证据**：第二天为 docker 申请出沙箱 14 次，为另外两类本机程序 5 次和 9 次。docker 走宿主守护进程，而那个 socket 在沙箱里被显式挡掉了（design.md 第二十二轮），所以这是必然的。

**可能的做法**：同一轮内**完全相同**的命令行重复申请时复用上一次的批准。要严格判定同一性（命令行、Cwd、轮次都相同），否则就是放行漏洞。收益有限，排在后面。

### 4. 审核期间用户看不到任何进度（优先级：低）

审核在跑的时候 agy 界面就是卡住 5～90 秒，没有"正在审核"的提示。没找到 hook 能往界面输出进度的机制，也许只能靠文档说明。

### 5. `setup` 仍然把整份模板写进配置文件（优先级：中）

**现状**：第二十二轮加了报告——`autoagy status` 会指出文件里钉着的旧默认值，并告诉你删掉那一项就跟着默认走。但根因没动：`defaultConfigFileText` 依然把几乎所有键写进 `config.json`，所以以后每改一个默认值，都要记得往 `SUPERSEDED_DEFAULTS` 里加旧值，忘了就又是一次"改了默认值但到不了任何老用户"。

**可能的做法**：只写用户真会改的那几个键（`mode`、`ownSandbox`、`writableRoots`、`rules`……），其余留在代码里当默认值，另外提供一份完整的注释版模板（`config.example.json`）给想照着改的人。代价是老用户的文件仍然是胖的，只有新装的人受益。

### 6. 审核进程继承了终端复用器的集成变量（优先级：低，未验证）

**推断**：guardian 是用 hook 的整份环境（`{...env, AUTOAGY_ROLE: 'guardian'}`）启动的 agy。在终端复用器里运行 agy 时，这份环境里有复用器的 pane id 和 socket 路径。如果用户级的 PreInvocation hook 会把「本次调用的对话 id」报告给复用器，审核对话就可能被记成这个 pane 的会话，复用器恢复时打开的就是一次审核，而不是用户自己的对话。本机确实装了这样一个 hook，但 agy 的日志不记录跑过哪些 hook，所以还没确认审核时它会不会触发。

**验证办法**：用一个假的 socket 路径和 pane id 发起一次 guardian 调用，看 socket 上有没有收到报告（要花一次审核的额度）。**修法候选**：审核进程的环境也按白名单重建；注意别把审核联网需要的变量（代理之类）一起丢掉。

## 二、安全方向的缺口

这些都不影响正常使用，也不会产生弹窗——是"比 Codex 更严"的方向上还没补的洞。

### 7. 没有审核质量的评测集（优先级：高，但要花额度）

**证据**：两天 121 次审核，111 批准、3 拒绝、7 超时。而 3 次拒绝里有 2 次是 `HOME=` 的误拦（已修），也就是说两天里真正拦下来的只有 1 条——agent 被拒之后用 python 套一层想绕过去那次。这说明不了它拦得住真正的坏动作。后来十二天的日志（834 次审核）里，2026-09-26 之后一次否决都没有——同样说明不了。

**可能的做法**：50～100 条样本（明显安全、明显危险、边界各一批，含 Codex 文档里举的那些），跑 guardian 打分，记假放行／假拦截率，结果写进 design.md。CI 里不跑（每次都花额度），本地一条命令跑。这是"这个插件到底有没有用"唯一的量化答案。

### 8. 绊线自己没有活性检查（优先级：中）

插件被删时 `~/.gemini/config/hooks.json` 里的兜底会拒绝一切工具调用，但没有任何机制确认 agy **还在**执行那条 hook。沙箱改写有 PostToolUse 自检（实测两天分别核对了 533 条和 469 条），绊线没有对应的东西。

**可能的做法**：绊线每次执行时写一个时间戳，`status` 报"最近一次绊线执行"，和 `last-hook-run.json` 一个路子。

### 9. D-Bus 没有被挡（优先级：中低）

第二十二轮把容器与虚拟机的守护进程 socket 显式挡掉了（docker、podman、containerd、cri-o、libvirt、`/run/systemd/private`），但**没挡 D-Bus**：`/run/dbus/system_bus_socket` 和会话总线。经由 polkit 的特权 D-Bus 服务是同一类洞——沙箱里递一个请求出去，活儿在沙箱外以 root 干。没挡的理由是挡了会弄坏普通桌面工具（通知、`systemctl --user`、`gio`），而这一类的使用频率远高于容器守护进程。

**要做的第一步是量**：先在一台桌面机上看看沙箱内的命令到底会用到哪些总线调用，再决定是整体挡掉、还是只挡系统总线。WSL2 上没有桌面会话，所以本机测不出来。

### 10. 嵌套 `.git` 扫描在慢文件系统上被截断（优先级：中）

**证据**：在 WSL2 的 9p 挂载上，扫描是被时间预算叫停的：`status` 显示最近几次只走了 285～491 个目录，标着 TRUNCATED。截断点以下的 `.git` 不会被挂成只读，命令跑完后也不会被检查。第二十四轮修的是「读取」的预算，这里卡住的是「遍历」的预算。worktree 多的工作区受影响最大。

**可能的做法**：worktree 不用靠遍历去找，直接读主仓库的 `.git/worktrees/*/gitdir` 就行（不运行 git，也不遍历）；遍历结果按对话缓存，只在目录的 mtime 变化时重新扫描；或者在 9p 上放宽时间预算——那样每条命令都会变慢，要先量一下再定。

## 三、没验证过的平台与场景

### 11. macOS：没有自带沙箱，也没人真机跑过（优先级：中）

Codex 在 macOS 上用 `sandbox-exec`（seatbelt），这里还没做，所以 macOS 上的形态是"每条非只读命令送审"——安全但吵。`commandGrant: "auto"` 在那里落成 `wildcard`，`networkGrants` 落成 `none`，两个都没有实测过。

### 12. Windows：executor 跑不了，也没人跑过（优先级：低）

`.mjs` 不能当程序运行，所以 `commandGrant` 只能是 `wildcard`；没有自带沙箱；`--dangerously-skip-permissions` 的检测要靠读进程参数，Windows 上读不到（现在按"不能问"处理，方向是安全的）。整体没有真机验证。

### 13. IDE 里的 Antigravity（优先级：低）

autoagy 读不到 IDE 的授权设置，所以 IDE 用户需要手动 `ownSandbox: "on"`。没有实测。

### 14. 子 agent 与并发会话（优先级：低）

挂载点回收的锁是按工作区取的，实测过"两个并发持有者都拿到共享锁"，但没有在真机上跑过主 agent ＋ 子 agent 同时干活的场景。第二天的日志里有 180 次 `agent-coordination`，说明子 agent 确实在用。

## 四、发布前的收尾

### 15. 版本

`v0.1.0` 还没打标签，标签说明里要写清楚：实验性，只在 Linux/WSL2 上实测过——agy 1.2.x 上长期使用，1.3.1 上做过冒烟测试。

### 16. transcript 超过 24 MB 时轮次计数会数少（优先级：很低，还没碰到）

`readTranscriptRows` 超过 24 MB 就只读头 2 MB ＋ 尾部，中间跳过；`countUserMessages` 数 `USER_INPUT` 得出的 `turnKey` 因此会偏小，可能让一次中断落到别的轮次上。实测本机最大的对话记录 1.87 MB，1116 行全部读到、计数准确，所以还没到。
